# ADR-0004：不保存 `passToken`，会话过期后重新扫码

日期：2026-10-27　状态：已接受（对应审计 #27）

## 背景

扫码登录后，米家返回的 `passToken`（账号级长期凭证）此前在 macOS 与 Windows 两端都被保存，但全仓库没有任何代码使用它——会话过期时直接提示重新扫码。存而不用只扩大泄露面（尤其审计 #16 之前它还被明文镜像），却不能换来任何体验收益。

另一种做法是"用起来"：会话过期时用 `passToken` 静默换取新的 `serviceToken`（开源社区有成熟流程）。这能把"每隔一段时间重新扫码"变成无感续期，但需要引入并长期跟随小米未公开的续期端点与参数，在没有真实账号可验证的环境里，静默续期失败的表现（循环失败、风控）难以充分测试。

## 决定

1. **登录成功后不再持久化 `passToken`**：两端的会话存储（macOS `MiSessionStore`、Windows `miCloudClient.ts`）只保留调用米家 API 必需的字段（`serviceToken`、`ssecurity`、userId、region 等）。
2. **旧数据迁移**：升级后第一次读取旧会话时剥掉 `passToken` 并重写存储，不需要用户重新登录。
3. **会话过期时**保持现状：明确提示用户重新扫码，不做静默续期。
4. 凭证的存放位置仍遵循 ADR-0002 与 #16 的修复：只存钥匙串（macOS）/ Windows 凭据管理器（Windows），不落明文。

## 后果

- 泄露面减小：钥匙串/凭据管理器里的会话即使被读走，也拿不到账号级的长期 `passToken`。
- 体验维持现状：用户仍需周期性重新扫码；这是接受本决定的主要代价。
- 若未来用户反馈续期体验问题，可以重开此决定：届时 `passToken` 只进钥匙串/凭据管理器，并且续期失败必须有明确的用户可见降级路径（回到扫码），绝不静默重试。
