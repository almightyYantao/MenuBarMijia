# ADR-0007：局域网直连（miIO）暂不推进，先做只读 spike

日期：2026-10-27　状态：已接受（对应审计 #63，探索项）

## 背景

冻结计划 v1 第 3 条希望"6 秒轮询 → 局域网直连/推送"。局域网直连（miIO 协议，UDP 54321，AES 加密）相比云端轮询：延迟从秒级降到几十毫秒、断外网可用、大幅减少对小米云的请求量（降低风控风险，见 #26 的修复）。开源社区已有成熟参考实现（python-miio 等）。

在动手前必须回答的问题（按 #63 原文）：

1. **支持范围**：Wi-Fi 设备大多支持 miIO 直连；BLE、Zigbee、Mesh 子设备要经过网关（多模网关 2 的本地协议与 miIO 不同），大概率仍走云端。混插环境下"哪些设备能直连"只能逐型号实测。
2. **安全方案**：设备 token 需要从云端设备列表换取，属于敏感凭证——若引入，必须只存钥匙串/凭据管理器（遵循 ADR-0004 与 #16 修复后的存储原则），绝不进 UserDefaults/localStorage。
3. **混合策略**：能直连的设备以局域网状态为准（更快），直连失败自动回落云端并在 UI 标注"本地不可用"；控制指令先本地后云端。状态来源切换必须有明确的仲裁规则（本地最近一次成功响应时间戳 > 云端则信任本地）。
4. **是否推进**：**暂不推进**。

## 决定

不做实现。原因：

- 审计的高/中优先级问题（凭证、更新信任、误操作防护、Windows 能力对齐）优先级更高，直连是大功能，插队会拖住整个修复节奏。
- 无法在本仓库现有测试环境验证：直连需要真实设备在真实局域网里响应，单测只能覆盖协议编解码，覆盖不了设备兼容性——这正是"支持范围"问题的核心。
- #26 修复后云端轮询已按场景降频（面板关 60 秒、低功耗 180 秒、锁屏暂停），风控压力已显著缓解，直连的紧迫性下降。

## 后续路径（若重新启动）

1. 先做**只读 spike**：对一台 Wi-Fi 插座（如 cuco.plug），在本地脚本里实现 miIO hello + 读状态，测延迟与稳定性；不写控制指令，不碰真实设备状态。
2. spike 结果（设备覆盖、token 获取链路、延迟数据）回填本 ADR，再决定是否立项。
3. 立项时：协议编解码放 `MijiaCore`（保持 Linux 可测），socket 层两端各自适配；token 走钥匙串/凭据管理器。
